# Repository Guidelines

## Project Structure & Module Organization

Terminal Canvas is migrating from Electron to Tauri 2. Electron remains the default app until the validation gates in `docs/rust-migration-plan.md` pass.

- `src/`: shared HTML/CSS/JavaScript renderer and xterm integration. The Electron host modules (`*.cjs`) remain as the reference implementation during migration; `bridge.js` implements the same renderer boundary for Tauri.
- `crates/tc-core/`: workspace validation, session/OSC parsing, assets, directories, and recovery logic.
- `crates/tc-pty/`: terminal processes, shell integration scripts, directory polling, backpressure, and cleanup.
- `crates/tc-hook/`: the standalone shell/session hook.
- `src-tauri/`: desktop commands, platform services, asset protocol, and app lifecycle. Its host actor owns mutable terminal and recovery state.
- `xtask/`: development checks, deterministic native icons, and Windows packaging.
- `vendor/portable-pty/`: pinned upstream source with a documented Windows process-creation Job Object patch; preserve its license and limit changes to the recorded patch.
- `tests/`: JavaScript unit tests, `golden/` parity fixtures, and Windows WebView2 E2E tests in `e2e/`.
- `src/assets/`: shared logo and generated native icons. `src/vendor/`, `target/`, `.cache/`, `release/`, `src-tauri/permissions/autogenerated/`, and `src-tauri/binaries/` are generated and ignored. `src-tauri/build.rs` declares the command permissions and regenerates their descriptors.

## Build, Test, and Development Commands

Use Node 22.12+ with npm 10 for the existing lockfile. `rust-toolchain.toml` pins Rust 1.95. Native Rust builds also require a C++20 compiler and the platform prerequisites listed in `README.md`.

- `npm ci`: install pinned development dependencies and prepare vendored xterm files.
- `npm start`: launch the current Electron app.
- `cargo build -p tc-hook`, then `cargo run -p terminal-canvas`: launch the Rust host with session capture.
- `cargo xtask check`: rustfmt, clippy, Rust tests (normal and test-only host), JavaScript syntax/unit tests, native icon checks, and golden parity.
- `cargo test --workspace`: Rust tests. Some parity tests require `node` on PATH.
- `npm test`: JavaScript unit tests.
- `npm run test:layout -- --verify-regression`: macOS rendered comparison with the immutable JavaScript UI and native WebKit; see `tests/visual/README.md`. Requires Xcode command line tools and an Electron test executable.
- `cargo xtask icons [--check]`: generate or verify native PNG/ICO files from the shared SVG using resvg.
- `cargo build -p terminal-canvas --features e2e`, then `npm run test:e2e`: Windows-only Playwright tests against WebView2. Build `tc-hook` first. PowerShell 7 is required in addition to the built-in Windows shells.
- `cargo xtask package-windows`: Windows-only NSIS/portable artifact preparation; requires the pinned Tauri CLI documented in the README.
- `cargo xtask package [--target <triple>] [--updater]`: this platform's packages (Windows installer and portable zip, macOS `.dmg`, Linux `.AppImage`/`.deb`) in `release/`. `--updater` signs the updatable ones and needs `TAURI_SIGNING_PRIVATE_KEY`.
- `cargo xtask release --tag vX.Y.Z --repo owner/name --input <dir> --output <dir>`: verifies every platform's signed packages against the committed updater key and writes `latest.json`. Tagging `vX.Y.Z` runs both in `.github/workflows/publish.yml` and creates a draft release.

A normal Rust launch uses the existing Electron data directory. Use `cargo run -p terminal-canvas --features e2e -- --smoke-test` for an isolated workspace. Test builds default to an isolated smoke profile even without flags. The `e2e` feature must never be enabled in release builds; compilation rejects that combination.

## Coding Style & Naming Conventions

Follow the language's standard conventions and the configured Rust formatter/lints. Use four spaces for JavaScript, avoid tabs and trailing whitespace, keep files focused on one responsibility, and prefer descriptive names.

Preserve workspace format 3, migrations from formats 1/2, validation order, and user-visible error messages. JavaScript limits count UTF-16 units. The renderer changes only where the host boundary requires it; migration work adds no product features or redesign.

## Testing Guidelines

Add meaningful behavior tests and regression tests for fixes. Pure host logic belongs in Rust tests; renderer behavior stays in JavaScript. Golden files record the reference host behavior: regenerate intentionally with `node scripts/capture-golden.cjs`, review the diff, and keep a corresponding Rust parity check. Renderer unit tests use captured JSON rather than importing the legacy host.

Host goldens do not validate layout. `tests/visual/` renders the actual pre-migration UI from its pinned Git commit, then compares current Chromium and WebKit controls at fixed viewport sizes. Keep screenshots and geometry reports in `.cache/`; preserve the negative control that detects the original shift.

Windows is the primary target. macOS/Linux results, Windows source type-checks, and skipped E2E discovery do not prove Windows runtime behavior. CI must pass on all three runners. The migration also requires ten consecutive native Windows E2E runs and manual desktop/clean-machine checks; record unverified gates in the migration plan.

## Commit & Pull Request Guidelines

Use concise, imperative commit subjects and keep each commit focused. Pull requests should explain the change and its purpose, link related issues where applicable, and list validation performed. Include screenshots or terminal recordings for visible changes and identify checks that could not run.

## Security & Configuration

Keep credentials, local configuration, generated output, and installed dependencies out of version control. Expose only the app's own commands to the local main webview. Keep OS operations behind host validation, preserve CSP/navigation/permission restrictions, and isolate all test profiles from user data. Test CLI substitutes must resolve to controlled local tools before invocation and must not contact real providers.

`src-tauri/src/updates.rs` checks GitHub releases only in release builds; debug, test, and E2E builds must never contact the update endpoint. The updater plugin's JavaScript commands stay ungranted; the renderer reaches updates only through `update_install` and host events. The release version lives in the root `Cargo.toml` alone (`tauri.conf.json` has none). The updater private key is a repository secret, never a file in the tree; `plugins.updater.pubkey` is its public half, and changing it strands every installed copy.
